## Two distinct, evidence-backed findings — READY TO POST WHEN AUTHORIZED

### 1. [#6478](https://github.com/OrchestratorInc/agent-orchestrator/pull/6478) — snapshot ID can be invalidated between allocation and boot
Owner: [mohakchakraborty2004](https://github.com/mohakchakraborty2004). Inspected head `b2ba705598538ff7436f6840c88f1f1d56fdb2a0`.
- `cloud/internal/httpapi/resource_handlers.go`: `projectSnapshots.Lookup` embeds the snapshot ID into a session's stored `ResourceProfile`; after `CreateSession`, it calls `sandboxWake` and launches `Ensure` asynchronously.
- `cloud/internal/projectsnapshot/builder.go`: `Ensure` can replace a stale stored snapshot and immediately call `VMs.DeleteSnapshot(previous)`. The `last_used_at` scheme protects the idle collector but does **not** protect a just-looked-up snapshot from *replacement*.
- `cloud/internal/reconcile/reconciler.go`: later `workerSpec` uses the saved `RootFS`; `provider.Create` fails with `r.fail` on errors other than capacity/duplicate; there is no missing-snapshot fallback in this path.
- Potential interleaving: session A looks up `sh-old` → builder for another or the same session publishes `sh-new` and deletes `sh-old` → reconciler calls VM Create with A's saved `sh-old`. **Static race identified; provider-level failure and frequency not reproduced.**
- Review suggestion: keep replaced snapshots alive for a safe launch grace/lease window, or retry a deleted-snapshot Create against the immutable harness base + checkout (without duplicate session creation); add a deterministic test locking the gap between Lookup and Create.
- Priority P1 candidate (user-visible cloud startup reliability); do not unilaterally redesign owner implementation.

Suggested comment:
> Thanks for the repository-scoped snapshot optimization. One potential startup race at this head: `createSession` looks up `sh-old` and stores it in `ResourceProfile` before the reconciler runs. Concurrent `Ensure` can replace the row and call `DeleteSnapshot(sh-old)` immediately; the delayed reconciler then tries `provider.Create(RootFS=sh-old)` and appears to fail rather than fall back. `last_used_at` protects the idle collector, not replacement. Could we hold previous snapshots through an in-flight launch grace/lease or handle deleted snapshot by falling back to the harness base? A deterministic Lookup(old) → Replace+Delete(old) → Create(old) test would pin the invariant. Source-level finding only; I haven't reproduced it against Freestyle.

### 2. [#5622](https://github.com/OrchestratorInc/agent-orchestrator/pull/5622) — buffer cap silently loses accepted keystrokes
Owner: [AgentWrapper](https://github.com/AgentWrapper). Inspected head `8485fb2f24eafb848fd68c19d7e9751ffd5cdfbc`.
- `frontend/src/renderer/lib/cloud-terminal-mux.ts` introduces `MAX_PENDING_INPUT = 64` and `pendingInput.shift()` on an unavailable socket, with no status or rejection returned by `sendInput`.
- `cloud-terminal-mux.test.ts` explicitly expects an 80-input burst to replay only `k16..k79`, silently discarding the first 16 inputs.
- The accepted-input invariant is violated: if an operator pastes or types during reconnect, the command they eventually execute may differ from what they typed.
- Request explicit visible overflow/rejection or disabling input *before* accepting too much; do not drop previously accepted input. Isolate this from the unrelated benchmark/blog changes and test connected → disconnected → 80 writes → reconnect.
- Priority P1 source-level correctness blocker; no packaged-app reproduction. The same queue on current main is unbounded, so this behavior is introduced by the PR.

Suggested comment:
> Thanks for the measurement work. One correctness issue in `cloud-terminal-mux.ts`: at 64 pending input entries the code silently evicts the oldest accepted keystroke via `pendingInput.shift()`. The new test codifies the loss (`k0..k15` vanish after reconnect). For a terminal, that can change a typed command/paste without warning. Could overflow instead reject or visibly disable input, while preserving the order of bytes already accepted? I'd want a disconnected 65+ inputs → reconnect regression that asserts no silent loss. Static review only; not a packaged-app test.
